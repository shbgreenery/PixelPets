# 机器与养殖面板易用性改造

日期：2026-11-25
状态：待评审

## 意图

当前机器面板把 9 台机器、14 个配方、队列与扩建全部平铺在一张 680×624 的卡片里，约合 3 屏；养殖面板约合 2 屏。玩家每天真正高频做的是**对这一台机器加料/收取**与**对这一只动物喂食/收取**，而建造、扩建、解锁配方是低频动作。两者占据同样的视觉权重，导致高频操作每次都要滚动定位。

本次改造的目标：把面板从"一条长列表"变成"左侧索引 + 右侧单对象操作台"，让高频操作在选中对象后一步完成，低频动作收进详情底部，并在顶栏保留少量兜底批量入口。

## 目标

- 加料、收取、加速对**单台机器**操作，且选中机器后一次点击完成。
- 喂食、收取、加速对**单只动物**操作，交互与机器面板一致。
- 面板长度不再随机器/动物数量线性增长到需要滚动定位：左栏索引在 9 台机器时无需滚动。
- 各面板按钮位置统一：条目右侧永远是该条目的主操作。
- 低频动作（建造、扩建队列、扩建畜舍、解锁配方）不与高频动作争夺视觉层级。

## 非目标

- 不改服务端规则数值、存档结构、动作语义。
- 不改订单面板与成就面板（本轮不涉及；订单是卡片式且无重复高频动作，成就只读）。
- 不做乐观 UI；动作仍等待服务端确认后刷新。
- 不改 1280×720 固定舞台与 `transform` 缩放机制。

## 约束

- 面板在固定舞台内：卡片宽 `min(680px, 92%)`，高 `calc(100% - 96px)` ≈ 624px。
- 视觉语义：琥珀 = 当前可做，草绿 = 生长中，麦黄 = 成熟，土红 = 短缺。新增元素必须沿用 `display/theme.ts` 的 token，不引入字面色号。
- 状态只由服务端改变；客户端所有动作仍走 `store.action()`。
- `GameStore` 每 5 秒轮询并 `notify()`，面板当前是 `list.replaceChildren()` 全量重渲染。选中项、分组折叠状态必须存在视图实例上，不能存在 DOM 上。
- `prefers-reduced-motion` 下不新增动画依赖。

## 已选方案

用户选择"合成甲"：左右分栏。

```
[机器]                                              [关闭]
┌────────────────────────────────────────────────────┐
│ 一键收取 3    一键加料 4    一键加速        沙漏 7  │
├──────────────┬─────────────────────────────────────┤
│ 可收取 3     │ 面包房                    队列 1/2  │
│  榨汁机 ●    │ 队列                                │
│  罐头厂 ●    │  面包         可收取       [收取]   │
│ 可加料 4     │  玉米面包     12:30        [加速]   │
│  磨坊   ●    │ 配方                                │
│  面包房 ○    │  面粉（小麦×2）            [放入]   │
│ 生产中 2 ▸   │  玉米面包（面粉×2 玉米×1） [放入]   │
│ 未建造 3 ▸   │ 队列 1/2                  [扩建]    │
└──────────────┴─────────────────────────────────────┘
```

选择理由：用户明确要求"收取、加料都对单个机器操作，更有针对性"。分栏让任何时刻只有一个对象处于可操作状态，配方选择不经过"默认配方"的猜测。

被放弃的方案：

- **单列 + 分组 + 行内展开**：加料一步完成，但详情不常驻，且"展开"状态在 5 秒轮询下容易丢失。用户不接受以详情常驻换取一步加料。
- **单列 + 每行配方按钮**：改动最小，但未建造机器仍占满长度，没有解决"一多就长"。

## 详细设计

### 布局与尺寸

卡片内部（扣除 padding 16 与 header）：

- 顶栏快捷条：高 44px，`sticky` 于左右分栏之上。
- 分栏容器：`display: grid; grid-template-columns: 168px minmax(0, 1fr); gap: 12px;`
- 左栏：自身可滚动，`overflow-y: auto`，细滚动条沿用 `SCROLL_CLASS`。
- 右栏：自身可滚动；队列与配方区独立，底部低频区固定。

左栏单项高度 32px，9 台机器 + 4 个分组标题 ≈ 416px，无需滚动。畜舍只有 3 项，左栏更短。

### 左栏：状态分组索引

状态由纯函数判定，优先级从高到低，每台机器只归入一个组：

| 状态 | 判定 | 分组 |
| --- | --- | --- |
| `collectable` | 已建，队列中存在 `readyAt <= now` | 可收取 |
| `addable` | 已建，队列未满，且至少一个**已解锁**配方材料足够 | 可加料 |
| `running` | 已建，队列中有未完成任务 | 生产中 |
| `idle` | 已建，队列为空且没有任何可加料配方 | 生产中（摘要显示"空闲"） |
| `unbuilt` | 未建 | 未建造 |

- 分组顺序固定：可收取 → 可加料 → 生产中 → 未建造。
- 分组标题右侧显示数量；点击标题折叠/展开，折叠状态存实例字段。
- 未建造分组默认**展开**：初始存档只有磨坊已建，折叠会让新玩家看不到建造入口。组内按 `unlockLevel` 升序，等级不足的条目置灰并显示 `Lv.N`。
- 每项内容：图标 + 名称 + 状态摘要。摘要示例：`×2`（可收取数量）、`0/2`（队列占用）、`Lv.6`（锁定）、`空闲`。
- 选中项：琥珀左边框 + 略亮的底色（沿用 `SURFACE.activeAmber`）。

### 右栏：单机器操作台

从上到下：

1. 标题行：`图标 + 名称`，右侧 `队列 x/y`，紧跟 `[加速]` 与 `[收取]` 两个机器级按钮。
2. 队列明细：每个 job 一行，只显示 `配方名` + 状态（"可收取"用草绿，或剩余时间用等宽字体），**行内不放按钮**。
3. 配方列表：仅列出 `recipe.machine === 当前机器` 的配方。已解锁：`配方名（材料×n）` + `[放入]`；未解锁：`配方名（需 Lv.N）` + `[解锁]`。`[放入]` 在队列已满或材料不足时禁用，并在行内说明缺什么（复用 `orderShortfall` 的思路，新增 `recipeShortfall`）。

**按钮粒度的决定（实现者拍板）**：服务端 `collectReady(machineId)` 一次收走该机器全部已完成任务，`useHourglass({kind:"machine"})` 只加速最早未完成任务并把后续任务整体前移。队列行没有独立 id，做不出真正的"按 job 收取/加速"。因此这两个按钮上提到标题行、按整机语义工作；队列表只读。这与用户要的"针对单台机器"一致，只是把"针对"的粒度定在机器而不是 job。
4. 低频区：`队列容量 x/y` + `[扩建队列（N 金币）]`，字号小一档，置于右栏底部。
5. 未建造机器：右栏只显示建造信息、建造条件与 `[建造（N 金币）]`；等级不足时写明 `需要等级 N`。

### 顶栏快捷条

保留三个兜底批量入口，按 `store.action()` 可用性禁用：

- `一键收取 n`：n = 所有机器中**可收取的任务数**（与左栏"可收取"组的机器数不同，组标题显示机器数，按钮显示任务数；实现时在按钮旁用小字注明"份"，避免歧义）。
- `一键加料 n`：n = **可加料的机器数**，与左栏"可加料"组的计数同口径，不模拟预计入队任务数。动作完成后用服务端返回的 `queued` 在 note 显示"已加料 X 台 / Y 份"。
- `一键加速`：依次给生产中的机器使用沙漏，沙漏用完即停，并用 note 提示。

单机操作是主路径，一键是兜底。这一取舍来自用户选择的分栏形态：若一键成为主路径，右栏的单机针对性就失去意义。

### 智能行为

1. **首次选中**：按"可收取 → 可加料 → 生产中 → 未建造"顺序选中第一条；无任何机器时选中第一台未建造。
2. **操作后跳转**：对选中机器执行动作后，若它仍属于原分组则保持选中；否则自动选中同一分组的下一条；该组为空时选中下一个非空分组的首条。避免玩家每次操作后回左栏寻找。
3. **轮询保持**：`selectedId` 与分组折叠状态保存在实例上，`render()` 重建 DOM 后恢复；若选中机器从状态中消失，回退到首次选中规则。
4. **状态摘要在左栏实时更新**：复用现有 250ms `refreshLabels` 的节奏？机器面板当前没有独立定时器，只依赖 `store.subscribe` 与 5 秒轮询。本次**不新增定时器**：剩余时间在 `render()` 时按 `Date.now()` 计算，5 秒刷新一次可接受；点击一次动作会立即刷新。新增定时器会让面板常驻重绘，与本次"减少无效渲染"的方向相反。

### 养殖面板

沿用同一骨架，层级为"容器 → 条目"：

- 左栏：三个畜舍（鸡舍/牛棚/羊圈）。每项摘要**显示聚合计数**，最多两项，例如 `可收取 2 · 待喂食 1`；没有可操作项时显示 `产出中 3` 或 `空`；未解锁显示 `Lv.N`。混合状态是常态，只显示单一状态会丢信息。
- 右栏：该畜舍的动物列表，每只一行；状态（饿着/产出中 mm:ss/可收取）在左，主操作在右（`[喂食]` / `[加速]` / `[收取]`）。这里的行级按钮是机器级动作分不出来、而动物动作天然按只的差异：`feedAnimal`/`collectAnimal`/`useHourglass({kind:"animal"})` 都接受索引，所以保留行级。
- 右栏底部低频区：`[买入（N 金币）]` 与 `[扩建畜舍（N 金币）]`，各附条件说明。
- 顶栏：`喂养全部 / 收取全部 / 加速全部`，作用于当前选中的畜舍（与机器面板的"全局一键"不同，因为畜舍是分组的，作用于当前舍更符合"针对性"）。

### 服务端新增动作

现有只有单机器的 `enqueue` / `collectReady` / `useHourglass`，没有批量。按 `plantAll` / `harvestAll` 的既有模式在 `server/core/slow-farm-core.js` 新增：

| 动作 | 输入 | 返回 | 语义 |
| --- | --- | --- | --- |
| `collectAllMachines` | 无 | `{ ok, items, collected, skipped }` | 遍历所有机器收集已完成任务；仓库满则跳过并计入 `skipped` |
| `enqueueAll` | 无 | `{ ok, queued, blocked }` | 按 `rules.MACHINES` 定义顺序遍历每台已建机器，每台反复放入"配方定义顺序中第一个材料足够的已解锁配方"，直到队列满或材料耗尽；材料不足的机器**跳过并继续下一台**，不全局停止。`queued` 为实际放入份数 |
| `useHourglassOnMachines` | 无 | `{ ok, used, stopped }` | 依次加速生产中的机器，沙漏用完返回 `stopped: "no_hourglass"` |

同步修改：

- `server/src/state/engine.ts`：加入 `ACTION_TYPES` 与 `handlers`。
- `server/core/slow-farm-core.js`：导出新函数。
- 客户端 `ACTION` 无需类型枚举（动作以字符串传递），但 `reasonText` 需要覆盖新增的 `blocked` 原因。

批量动作放服务端而不是客户端循环调用，理由：保持"改变状态的逻辑只在服务端"的既有约束，且一次往返、一次写盘，避免中途失败留下半完成状态。

### 不变的部分

- `GameStore`、`api/client.ts`、动作请求链路。
- 订单、成就、商店、农场、仓库面板。
- 存档结构与 `rev` 机制。

## 测试计划

- **core**（`server/core/tests/`）：为三个新动作补 assert 用例，覆盖正常、仓库满跳过、材料耗尽停止、沙漏用完停止；`enqueueAll` 还要覆盖"某台无料继续下一台"与多配方选择顺序。
- **纯函数**（`client/src/display/`）：新增 `machineStatus` / `machineGroup` 的单元测试；`animalView` 增加畜舍聚合计数字段的测试。`pickAutoRecipe` 只在服务端存在，不写客户端版本，避免两套模拟口径。
- **面板**（`client/src/ui/`）：新增 `MachinePanel.test.ts`，用 jsdom 断言分组渲染、选中切换、点击"放入"提交的参数、轮询后选中保持；`AnimalPanel.test.ts` 同理。
- **集成**：`FarmView.test.ts` 的入口与开关逻辑不变，仅确认没有回归。
- **手动**：在浏览器里用一份后期存档（9 台机器、3 种畜舍）检查首屏无滚动、加料一步完成、轮询 5 秒后选中不丢。

## 风险

- **选中丢失**：全量重渲染 + 5 秒轮询是最大风险。缓解：把选中与折叠状态放在实例上，并补一个"轮询后选中保持"的 jsdom 测试。
- **左栏拥挤**：未建造 8 台时左栏约 12 项，仍在 592px 内；若后续机器数量增加，左栏自身滚动兜底。
- **一键加料的配方猜测**：只影响顶栏兜底入口，单机路径不经过猜测；若玩家从不使用一键，此功能无副作用。
- **状态判定与 `machineView` 重复计算**：新增纯函数应复用 `machineView` 的队列结果，避免两套剩余时间逻辑。
